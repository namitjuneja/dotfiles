# Hyprland Config — Setup Notes

This documents all customizations made to the default Hyprland config
(`https://github.com/hyprwm/Hyprland/blob/main/example/hyprland.conf`),
plus every package installed during setup. Use this to restore the setup
from scratch.

## Config File Structure

```
~/.config/hypr/
├── hyprland.lua      # main config, native Lua format (Hyprland 0.55+) — see migration section below
├── hyprland.conf     # legacy config, kept as a reference/fallback — NOT loaded while hyprland.lua exists
├── monitors.conf     # generated by nwg-displays, sourced externally
├── hyprpaper.conf    # wallpaper config
├── hyprlock.conf     # lock screen config
├── hypridle.conf     # idle/sleep management config
└── workspaces.conf   # (empty/minimal)
```

> **Which file is actually loaded?** Hyprland checks for `hyprland.lua` **once, at startup
> only** — if found, it's used instead of `hyprland.conf` and the `.conf` file is ignored
> entirely for that session. This check does NOT re-run on `hyprctl reload`, only on a full
> Hyprland restart (log out/in). Confirm which one is active with:
> ```bash
> hyprctl systeminfo | grep configProvider   # "lua" or "hyprlang"
> ```

## Changes from Default hyprland.conf

### Monitors

**Default:**
```
monitor=,preferred,auto,auto
```

**Custom:**
```
monitor=,preferred,auto,2
monitor=HDMI-A-2,3440x1440@50,0x0,1.6
monitor=DP-4,3440x1440@50,0x0,1.6
```

- Ultrawide monitor entries for both `HDMI-A-2` and `DP-4` at 3440x1440@50Hz, scale 1.6 (covers either port being used)
- Default/fallback monitor uses scale factor `2` instead of `auto`
- `monitors.conf` is generated by `nwg-displays` and can be used to manage
  monitor layout via GUI. The `hyprland.conf` entry takes precedence if not
  sourced separately.

> **Jankiness root cause (resolved):** The monitor was initially running at `@29.99` (~30fps),
> which caused the cursor and all animations to look choppy and laggy. Switching to `@59.98`
> (60fps) fixed it entirely. If everything feels janky, check the refresh rate first.
>
> **Other methods not yet tried (if jankiness returns):**
> - Remove fractional scaling (set scale to `1.0`) — fractional scaling can cause rendering
>   artifacts and performance issues on some setups.

#### Named persistent workspaces (1–9)

Workspaces 1–9 are named and marked `persistent:true` so they always exist,
even when empty. This lets Waybar's `hyprland/workspaces` module see real
workspace state (window counts, urgent flags) and apply CSS classes like
`button.empty` and `button.urgent` correctly.

```
workspace = 1, name:1: Firefox, persistent:true
...
workspace = 9, name:9: Music, persistent:true
```

> **Note:** Use Hyprland's `persistent:true` rather than Waybar's
> `persistent-workspaces` — Waybar's approach creates hollow stubs that
> don't carry real workspace state, so CSS classes won't work.

### Layout

**Default:** `dwindle` layout  
**Custom:** `master` layout with `new_status = slave`

New windows open as slaves (tiled alongside the master) rather than becoming
the new master. Use `Super + \` to swap the focused window with the master,
`Super + ]` / `Super + [` to add/remove the focused window from the master
area. Use `Super + R` to cycle the master area's orientation (left → top →
right → bottom → center); the current orientation shows as an icon in Waybar
(see [custom/orientation module](#customorientation-module)).

Switching focus between master and stack: `Super + H/J/K/L` (or the arrow
equivalents) are directional, so which key moves toward the master area
depends on the current orientation from `Super + R`. `Super + Tab` /
`Super + Shift + Tab` cycle through windows in master → stack order
regardless of orientation, so they're the more reliable choice after
changing orientation.

## Migration to hyprland.lua (Hyprland 0.55+)

Hyprland 0.55 deprecated its old `hyprlang` config syntax (`hyprland.conf`) in favor of a
native Lua config (`hyprland.lua`). `hyprland.lua` is a line-by-line translation of the old
`hyprland.conf` using the new `hl.*` Lua API — see
[the official example config](https://github.com/hyprwm/Hyprland/blob/main/example/hyprland.lua)
and the [wiki](https://wiki.hypr.land/Configuring/Start/) for the full API.

Syntax mapping used throughout the translation:

| hyprlang (old) | Lua (new) |
|---|---|
| `monitor=HDMI-A-2,3440x1440@50,0x0,1.6` | `hl.monitor({ output="HDMI-A-2", mode="3440x1440@50", position="0x0", scale=1.6 })` |
| `general { gaps_in = 5 ... }` | `hl.config({ general = { gaps_in = 5, ... } })` |
| `bind = $mainMod, F, togglefloating` | `hl.bind(mainMod .. " + F", hl.dsp.window.float())` |
| `windowrule { name = x; match:class = y; opacity = 1 }` | `hl.window_rule({ name="x", match={class="y"}, opacity="1" })` |
| `workspace = 1, name:1: Firefox, persistent:true` | `hl.workspace_rule({ workspace="1", name="1: Firefox", persistent=true })` |

### Breaking change: `hyprctl dispatch` / `hyprctl keyword` no longer take legacy syntax

Several keybinds shelled out to `hyprctl dispatch <name> <args>` (e.g. for cycling windows)
or `hyprctl keyword <option> <value>` (e.g. for toggling a setting from a keybind). Under
the Lua config, **both of these old CLI syntaxes are gone** — they now expect an actual Lua
expression as their argument, and `keyword` is disabled entirely:

```bash
# old syntax — silently fails under the lua config (no visible error until you check
# `hyprctl configerrors`, which is what made these bugs hard to notice)
hyprctl dispatch cyclenext
hyprctl dispatch fullscreen 1
hyprctl keyword decoration:dim_inactive false

# new syntax — dispatch takes a lua expression as a string
hyprctl dispatch "hl.dsp.window.cycle_next({next=true})"
hyprctl dispatch "hl.dsp.window.fullscreen({mode=\"maximized\"})"

# keyword is replaced by eval, calling the same hl.config(...) used in the config file itself
hyprctl eval "hl.config({decoration={dim_inactive=false}})"
```

Also note: `hyprctl getoption <x> -j` now reports booleans under a `.bool` field instead of
the old `.int` (0/1) field — any script parsing that JSON needs updating too.

This broke three keybinds that were fixed as part of this migration:

- `Super + Tab` / `Super + Shift + Tab` — cycle windows (`hyprland.lua:339-355`)
- `Super + D` — toggle inactive-window dim (`hyprland.lua:398`)
- `Super + A` — toggle animations on/off (`hyprland.lua:401`)

**Debugging tip:** `hyprctl configerrors` doesn't just show config *parse* errors — it also
surfaces the most recent *runtime* Lua error from a triggered keybind. If a bind that used to
work stops doing anything, trigger it once and immediately check `hyprctl configerrors`.

### Smoother window switching while maximized

The `Super + Tab` cycle-window bind needs to briefly un-maximize the current window and
re-maximize the next one (otherwise Hyprland keeps showing the old fullscreen window even
after focus moves to the next one). The naive order — unmaximize old → switch focus →
maximize new — causes a visible flicker down to the tiled layout and back:

```bash
# naive order: flickers, since the old window drops to tiled for a frame
hyprctl dispatch "hl.dsp.window.fullscreen({mode=\"maximized\"})"   # unmaximize old (visible!)
hyprctl dispatch "hl.dsp.window.cycle_next({next=true})"
hyprctl dispatch "hl.dsp.window.fullscreen({mode=\"maximized\"})"   # maximize new
```

Fixed by reordering so the new window's maximize-in animation covers the old window, and
only *then* clearing the old window's maximized flag (now hidden underneath, so no flicker):

```bash
old=$(hyprctl activewindow -j | jq -r .address)
hyprctl dispatch "hl.dsp.window.cycle_next({next=true})"
hyprctl dispatch "hl.dsp.window.fullscreen({mode=\"maximized\", action=\"set\"})"                       # new window covers screen
hyprctl dispatch "hl.dsp.window.fullscreen({mode=\"maximized\", action=\"unset\", window=\"address:$old\"})"  # old one, now hidden, drops its flag
```

### Live push-updates to Waybar via Hyprland's Lua event system

Hyprland's Lua config exposes an event system (`hl.on(eventName, callback)`) for reacting to
compositor events — used here to tell Waybar to redraw its window list the instant something
relevant happens, instead of Waybar polling on a timer (see
[Waybar → custom/windows](#customwindows-module) below for the other half of this):

```lua
local function refreshWaybarWindows()
    hl.exec_cmd("pkill -RTMIN+8 waybar")  -- SIGRTMIN+8: matches "signal": 8 in modules.json
end
for _, ev in ipairs({ "window.active", "window.fullscreen", "workspace.active", "window.open", "window.close", "window.title" }) do
    hl.on(ev, refreshWaybarWindows)
end
```

`pkill -RTMIN+8 waybar` sends the Unix realtime signal `SIGRTMIN+8` to the waybar process —
a generic "ping" the OS delivers to a running program without any files or sockets involved.
Waybar is configured to listen for that exact signal on one specific module and re-run its
script the moment it arrives (see below).

### idle_inhibitor module

- `󰛊` (outline) — idle inhibitor off; system will sleep/lock normally
- `󰅶` (filled, green) — idle inhibitor on; screen stays awake indefinitely

### custom/windows module

Replaced the built-in `hyprland/window` module (center of the bar) — it only ever shows the
single currently-focused window's title, so maximizing a window hid every other window on
that workspace from the bar, and two windows of the same app (e.g. two Firefox windows) were
indistinguishable since it doesn't show titles either.

`custom/windows` (`~/.config/waybar/scripts/workspace-windows.sh`) instead lists **every**
window on the current workspace, with both the app name and its window title:

```bash
hyprctl clients -j | jq -r --arg ws "$ws" --arg active "$active" '
  [ .[] | select(.workspace.id == ($ws | tonumber)) ] |
  map( (.class) + "  " + (.title | trunc(36)) )
  | join(" ")
'
```

The currently-focused window is wrapped in a pango `<span>` tag that inverts the bar's own
foreground/background colors, so it visually pops:

```
"<span background=\"#e6e8ee\" foreground=\"#0b1220\" weight=\"bold\">  firefox  GitHub  </span>"
```

**Live updates, not polling:** the module is configured with `"interval": "once"` and
`"signal": 8` — it does *not* refresh on a timer. Instead, Hyprland pushes a refresh signal
(`pkill -RTMIN+8 waybar`) the instant the focused window, fullscreen state, or workspace
changes (see [Migration to hyprland.lua → live push-updates](#live-push-updates-to-waybar-via-hyprlands-lua-event-system)
above for the Hyprland-side half of this). This replaced an earlier `"interval": 1`
(poll-every-second) approach, which had a visible ~1s lag between switching windows and the
bar catching up.

> To manually trigger a refresh for testing: `pkill -RTMIN+8 waybar`.

### custom/orientation module

Right side of the bar, next to the idle inhibitor. Shows which way the `master` layout is
currently split (see [Layout](#layout) — `Super + R` cycles it) as a single arrow icon:

- `⬅` left, `⬆` top, `➡` right, `⬇` bottom, `⏺` center

**Why this needs state tracking, not a live query:** `hyprctl getoption master:orientation`
only ever reports the static config default — `layoutmsg` changes the orientation
per-workspace at runtime, and Hyprland has no IPC command that exposes that live
per-workspace value. So `Super + R` is wired to
`~/.config/waybar/scripts/orientation-cycle.sh`, which computes the next orientation itself
(cycle order taken from Hyprland's `eOrientation` enum in `MasterAlgorithm.hpp`: left → top →
right → bottom → center → left), records it in `~/.cache/hypr-master-orientation` keyed by
workspace id, *then* dispatches that same value **explicitly**
(`layoutmsg orientationleft` / `orientationtop` / ... rather than the relative
`orientationnext`). Dispatching explicitly rather than relatively matters: since there's no
way to query Hyprland's live value, a relative `orientationnext` dispatch would let the cache
silently drift out of sync with reality forever if anything ever changed the orientation
outside this script. Dispatching the exact value just written to the cache makes every
keypress self-correcting — it forces reality to match the cache rather than assuming it
already does. `master-orientation.sh` (the module's `exec`) just reads that cache for the
active workspace, falling back to the config default for any workspace that hasn't been
cycled yet.

Same live-update pattern as `custom/windows`: `"interval": "once"` with `"signal": 9`, no
polling — the icon updates the instant `Super + R` is pressed.
